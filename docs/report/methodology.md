# Methodology

The pipeline converts first-person gameplay footage into BEV player localization through 4 major stages: player detection, multi-object tracking, depth estimation, and BEV projection. The pipeline takes RGB video frames as input and produces camera-relative BEV player positions as output.

```pipeline
direction: TB

I[Input]
---
tooltip: Input
color: grey
type: io
---

A[Detection]
---
link: ../methodology/#detection
tooltip: Identifies player locations from individual RGB frames using an object detector.
color: blue
---

B[Tracking]
---
link: ../methodology/#tracking
tooltip: Associates detections across frames to construct continuous player trajectories.
color: orange
---

C[Heuristic Depth]
---
link: ../methodology/#heuristic
tooltip: Estimates depth using geometric assumptions based on player bounding box size.
color: green
---

D[MiDaS Depth]
---
link: ../methodology/#midas
tooltip: Uses monocular depth estimation to infer scene depth from RGB frames.
color: red
---

E[BEV Estimation]
---
link: ../methodology/#bev-estimation
tooltip: Transforms detections into camera-relative BEV coordinates.
color: purple
---

O[Output]
---
tooltip: Output
color: grey
type: io
---

I --> A
A --> B
B --> C
B --> D
C --> E
D --> E
E --> O
```

The pipeline was designed around three constraints:

- monocular RGB input only
- limited computational resources
- requirement for interpretable intermediate outputs

More on design decisions [here](discussion.md#design-decisions).

## Detection
The detection stage takes RGB video frames as input and outputs player bounding boxes for every detected player in each frame.

The <a href="https://docs.ultralytics.com/models/yolo26" target="_blank" rel="noopener">Ultralytics YOLO26m</a> model was selected as the object detector for this pipeline. <abbr title="You Only Look Once">YOLO</abbr> is a single-stage object detection architecture that predicts object locations and classifies detected objects from an input image through a <abbr title="Convolutional Neural Network">CNN</abbr>. Unlike two-stage detectors, YOLO performs detection in a single forward pass for more efficient video data processing. YOLO26 is the newest version of the YOLO family of models with improved performance. More on this topic in the <a href="https://arxiv.org/abs/2606.03748" target="_blank" rel="noopener">Ultralytics YOLO26 paper</a>.

For this project, only the **person** class is detected. The detector outputs:

- Bounding box coordinates: ```(x_min, y_min, x_max, y_max)```
- Detection confidence score
- Frame index

At this stage, detections are independent between frames. The model does not know whether two detections from consecutive frames belong to the same player. Persistence is introduced in the tracking stage.

The confidence threshold is an important detection parameter. A lower threshold increases recall by allowing more possible detections but may introduce false positives. A higher threshold improves precision but may miss players under challenging conditions such as occlusion or poor visibility.

## Tracking
The tracking stage takes player detections as input and assigns persistent identities across frames. A <abbr title="Multi-Object Tracking">MOT</abbr> algorithm is used to process independent frame-level predictions from the detection stage. The tracker associates detections across consecutive frames to create continuous player trajectories.

<a href="https://supervision.roboflow.com/trackers/" target="_blank" rel="noopener">ByteTrack</a> was selected as the tracking algorithm due to its ability to use both high-confidence and low-confidence detections during association. Candidate detections are associated to existing tracks using motion prediction and bounding box overlap before new tracks are initialized. This improves tracking robustness when players may become partially occluded or temporarily difficult to detect. 

ByteTrack also relies less on appearance embeddings to identify people and establish continuous identity, good for instances where tracked people have similar clothing and features (e.g. soccer matches where players all have the same jersey), or in the case of this project, have the exact same appearance.

ByteTrack consists of two main stages:

- Detection association
    - Matches detections between consecutive frames.
    - Uses motion information and bounding box similarity.

- Track management
    - Creates new tracks.
    - Maintains existing tracks.
    - Removes inactive tracks.

Many parameters are important to the tracking process. Here are 3 parameters that this project focuses on in order to accurately associate detections and to maintain stable trajectories for later BEV localization.

| Parameter | Purpose |
|-----------|---------|
| ```track_activation_threshold``` | Determines the minimum confidence required before creating a new track |
| ```lost_track_buffer``` | Controls how long an inactive track is maintained before removal |
| ```minimum_consecutive_frames``` | Prevents short-lived false detections from becoming tracks |

The tracking output contains:

- Bounding box coordinates
- Detection confidence
- Track ID
- Frame index

At this stage, track IDs represent persistent tracked objects rather than known player identities.

## BEV localization
The BEV localization stage estimates the spatial position of players from RGB frame visual cues such as perspective, the player's apparent size, and their location within the image.

This process consists of two major steps:

- Depth extraction
- BEV estimation

In this project, 2 depth extraction approaches are compared:

- Geometric heuristic method
- Learned monocular depth estimation method using MiDaS

Both methods produce estimated depth values that are then converted into camera-relative BEV coordinates.

### Heuristic
The heuristic depth estimation method estimates player distance using geometric assumptions. The method assumes that the apparent size of a player's bounding box is inversely proportional to their distance from the camera. Larger bounding boxes correspond to closer players, while smaller bounding boxes correspond to farther players. That is:

    depth ∝ player_height / bbox_height

This method requires:

- Player bounding box height
- Camera <abbr title="Field-Of-View">FOV</abbr>
- Assumed player height

In this project, the assumed player height and camera projection constants are combined into a single scale constant (`depth_scale`) rather than exposed as separate parameters. The estimated depth is calculated using the relationship between object size, camera projection, and distance.

However, this approach relies on several assumptions:

- Player models have consistent physical height.
- Bounding boxes accurately represent the player body.
- Camera projection parameters are known.

Thus introducing many [limitations](discussion.md#limitations).

The main tuned parameter is camera FOV, which corrects the implicit assumption that the original horizontal-offset projection has a fixed ~90° camera FOV. `fov_scale` rescales the horizontal (`bev_x`) axis independently of depth (`bev_y`) to correct any mismatch with the camera's true FOV. `depth_scale`, which is a uniform multiplicative constant impacting the heuristic method's raw depth magnitude, was **not** tuned, but was a part of the calibration process for evaluation later in the pipeline.

### MiDaS
The MiDaS method uses a learned monocular depth estimation model to predict depth directly from RGB images. The <a href="https://pytorch.org/hub/intelisl_midas_v2/" target="_blank" rel="noopener">MiDaS DPT_Hybrid
</a> model was the medium-sized model selected due to hardware limitations while able to maintain reasonable depth estimation performance.

Unlike the heuristic method, MiDaS does not require assumptions about player size. Instead, the model learns visual patterns associated with depth during training.

The MiDaS process:

```pipeline
A[frame.png]
---
tooltip: Input RGB frame
color: purple
---

B[depth_map.npy]
---
tooltip: Generate dense depth map
color: red
---

C1[Depth value for bbox 1]
---
tooltip: Extract depth values corresponding to player bounding boxes
color: orange
---

C2[Depth value for bbox 2]
---
tooltip: Extract depth values corresponding to player bounding boxes
color: orange
---

C3[...]
---
tooltip: Extract depth values corresponding to player bounding boxes
color: orange
---

A --> B
B --> C1
B --> C2
B --> C3
```

The generated depth map contains relative depth information for every pixel in the frame and is stored as a ```.npy``` file.

Because the model processes every extracted frame independently, this stage has the highest computational cost in the pipeline.

For each tracked player:

- The corresponding bounding box is located on the depth map.
- A depth window is extracted around the center of the base of the detection, representing a more accurate positional location at the foot of the player.
- The mean depth value is used as the player's estimated depth.

The depth window parameter controls the region sampled from the depth map. A smaller window provides more localized measurements but is more sensitive to noise, while a wider window smooths over per-pixel depth noise but risks including background pixels.

Additional parameters include:

| Parameter | Purpose |
|-----------|---------|
| ```low_pct``` | Removes extreme (low) depth values |
| ```high_pct``` | Removes extreme (high) depth values |
| ```fov_scale``` | Adjusts depth projection scaling |

The `low_pct` / `high_pct` percentile bounds can normalize raw MiDaS depth output into a stable 0–1 range. These bounds are computed **once per video** from a sample of frames, since MiDaS's raw depth output is only relative within a single inference. Normalizing independently per frame causes the same real-world distance to map to different values depending on what else was visible in that frame.

Note the distinction between two different depth values in this pipeline: the full per-pixel depth map (MiDaS only, saved separately as a `.npy` file per frame) and the single scalar depth value extracted for each player's bounding box, which both methods produce and which is saved directly alongside `bev_x`/`bev_y` in `estimations.parquet` rather than as a separate intermediate file.

### BEV Estimation
The BEV estimation stage converts detections and extracted depths into camera-relative spatial coordinates.

Given:

- Player bounding box position
- Estimated depth
- Camera parameters

the horizontal BEV position is calculated from the player's offset relative to the image center. The vertical BEV coordinate corresponds to the estimated depth. That is:

    bev_x = normalized_horizontal_offset * player_depth * self.fov_scale
    bev_y = depth

The final output represents each player as:

    (track_id, frame_id, bev_x, bev_y)

These coordinates are camera-relative and are later transformed into world coordinates during evaluation using synchronized ground truth camera information.

## Evaluation metrics
The final BEV localization performance is evaluated using:

| Metric | Measures | Lower/Higher Better |
|--------|----------|---------------------|
| Euclidean positional error | Distance between predicted player position and ground truth position. Evaluates absolute localization accuracy. | Lower |
| Relative spatial accuracy | Whether the predicted spatial relationships between players are preserved. Evaluates whether the pipeline correctly captures the formation and arrangement of players even when absolute coordinates contain errors. | Higher |
| Trajectory consistency | Whether predicted trajectories remain stable over time. Important because localization should represent continuous player movement rather than independent frame-level predictions. | Higher |

Additional evaluation metrics for individual pipeline stages are described in their respective sections.
